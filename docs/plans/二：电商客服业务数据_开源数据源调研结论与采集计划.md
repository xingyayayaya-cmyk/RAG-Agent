## 0. 结论摘要

**搜完的结论：6 类数据里 4 类有非常合适的开源数据可直接用，1 类需拼装，1 类（售后政策文档）基本没有现成的，需要构造。**

| 类别 | 结论 |
|---|---|
| ✅ 直接可用 | FAQ/客服问答对、订单数据、意图标注、情绪标注 |
| ⚠️ 需拼装 | 商品库（1 万 SKU）—— 无「量级 + 完整参数 + 价格 + 平台」一步到位的现成数据 |
| ❌ 需构造 | 售后政策文档 —— 只有字段规范和规则代码，无中文政策语料 |

**关键瓶颈不是数据本身，而是获取方式**：Hugging Face / GitHub / ModelScope 可全自动拉取；**天池、百度网盘必须手动登录下载**。这直接影响排期。

| 业务数据 | 开源可得性 | 最佳候选 | 建议 |
|---|---|---|---|
| FAQ / 客服问答对 | ✅ 非常丰富 | 淘宝客服对话、EcomInstruct、Mix-Ecom | 直接用 |
| 订单数据 | ✅ 能找到 | 天池模拟交易（含金额/平台） | 直接用 |

## 2. 逐项详细

### 2.1 FAQ / 客服问答对 —— 最容易，量最大

| 数据集 | 规模 | 特点 |
|---|---|---|
| 淘宝客服对话数据集 | 100 万 session-response | 直接当 FAQ 快速通道 + 多轮对话语料 |
| EcomInstruct / EcomGPT | 250 万条电商指令 | 覆盖售前 / 物流 / 售后 |
| Mix-Ecom | 4,799 条混合型电商对话 | **明确标注售前/物流/售后**，带 82 条领域规则 |
| THU-StarLab/CustomerService | 8.7 万条客服 QA | 中文客服问答对 |
| ChineseNlpCorpus 百度知道系列 | 海量 | 联通 / 保险 / 金融等问答对，可作补充 |

> Mix-Ecom 是这里性价比最高的：规模适中、**自带意图标签**、还带 82 条领域规则——意图标签正好补 BERT 4 分类的冷启动训练数据，领域规则可以直接喂给「规则优先」层。

### 2.2 订单数据

| 数据集 | 规模 | 评价 |
|---|---|---|
| **天池 · 电商用户行为分析（模拟交易）** | — | **最合适**：12 字段（用户姓名/性别/城市、商品 ID/名称/单价/数量/金额、平台），覆盖天猫/淘宝/京东/拼多多/苏宁/1688 六平台，CSV 直接可用，**含金额** —— 正好支撑「大额转人工」演示 |
| 天池 · 淘宝用户行为（真实） | 1 亿条 | 真实但字段少、**无金额**，不适合做金额风控演示 |

> 决策要点：**必须选有金额的那份**。没有金额字段，「大额风险转人工」这条核心链路就演示不出来。

### 2.3 意图路由 + 情绪检测的标注数据

| 用途 | 数据集 | 说明 |
|---|---|---|
| 意图（订单 / 售前 / 售后） | **Mix-Ecom** | 最贴切，标签体系与目标 4 分类几乎对齐 |
| 强情绪 | **CCSE-CS**（GitHub，EMNLP 2026） | 9,478 对话，带共情 / 情绪策略标注 |

### 2.4 商品库 —— 最需要动脑的一块

| 数据集 | 提供什么 | 缺什么 |
|---|---|---|
| JDivPS（京东商品搜索） | 商品名 / 类目 / 品牌 / 尺寸 / 属性 / 颜色 | 已 token 化需 pickle 解，**无价格** |
| PAd1M（京东广告） | sku 标题 / 类目 / 卖点 | 无价格、无完整参数 |
| 天池 216886 商品字段 | 名称 / 类别 / 单价 / 平台 | 可补**价格**维度 |

**问题**：没有「1 万条 + 完整 SKU 参数 + 价格 + 平台」一步到位的现成数据，必须拼装。

### 2.5 售后政策文档 —— 唯一的明显缺口

搜到的只有：Google `MerchantReturnPolicy` 结构化规范、退款决策引擎代码（规则写死在代码里）、知识源字段规范。

**没有现成的「淘宝 / 京东 / 拼多多各平台退换货政策」中文文档语料。**

## 3. 数据 → 现有系统的落点映射

这一节是原调研里没有、但开工前必须定的：每份数据最终进哪个模块、哪张表、哪个 collection。

| 数据 | 落点 | 处理动作 |
|---|---|---|
| FAQ 问答对 | MySQL `faq` 表 + BM25 索引（`bm25_search.py`，阈值 0.85） | 清洗去重 → 打 intent 标签 → 建 BM25 |
| 订单数据 | MySQL `orders` 表 + `adapters/order.py` mock | 字段重命名对齐 schema，金额/手机/地址做脱敏种子 |
| 商品库 | Milvus `ecommerce_kb` + `adapters/product.py` mock | 走 `document_processor.py` 父子切分入库 |
| 售后政策文档 | Milvus `ecommerce_kb`（独立 partition） | `document_processor.py` 解析 → 切分 → 向量化 |
| 意图标注（Mix-Ecom） | 训练 `query_classifier.py` 的 4 分类 | 需扩为 订单/售前/售后/通用，每类 ≥500 条 |
| 情绪标注（CCSE-CS） | 风控关键词表 + LLM prompt 调优 | 抽高频负向词补关键词表；用标注集校准 LLM 分级阈值 |
| RAGAS 评测集 | `ragas_evaluate.py` | 从 FAQ + 政策文档构造 QA 对，换域重建基线 |

**字段对齐要求（商品库）**

```
sku_id, platform, title, category_path, brand, spec,
price_current, price_origin, stock_status, params_json,
image_urls, shelf_status, updated_at
```

**字段对齐要求（订单）**

```
order_id, user_id, platform, sku_id, sku_title, qty,
amount_total, amount_pay, status, pay_time, ship_time,
logistics_no, receiver_name(脱敏), receiver_phone(脱敏),
receiver_addr(到区县), created_at
```

## 4. 我的处理建议

| 数据 | 建议 | 理由 |
|---|---|---|
| FAQ、订单、意图/情绪标注 | **直接用开源数据** | 负责下载、清洗、转成现有系统能吃的格式 |
| 商品库 1 万条 | JDivPS / 天池做「真实骨架」，再**合成补齐价格和平台字段** | 合成可控、无授权风险、字段能精确对齐 SKU 需求 |
| 售后政策 2000 条 | **按各平台真实规则构造**：淘宝/京东/拼多多/抖音/1688 的 7 天无理由、15 天换货、运费险、食品/定制/内衣不适用等 | 量不必真到 2000，**写 200~300 条高密度规则，再切分成 2000 chunk** 即可 |

> 售后政策这条思路是对的：RAG 检索的单位是 chunk 不是文档，200~300 条高密度规则切分后完全能撑起 2000 chunk 的检索规模，而且密度高、噪声少，检索质量反而更好。

## 5. 需要你拍板的 3 个方向

### 方向 1：商品库和订单 —— 真实开源数据 vs 合成

| 选项 | 优点 | 缺点 |
|---|---|---|
| A. 真实开源（天池 / 京东） | 分布真实 | **需你手动登录下载**；字段不齐；授权需确认 |
| B. **合成高仿真数据（推荐）** | 全自动、可复现、无授权风险、字段完全对齐 SKU schema | 分布与真实有偏差，后期需用真实数据校准 |

**倾向：选 B。** 理由是可复现、无授权风险、字段完全对齐；真实数据留到 M3 评测阶段再引入做校准，那时数据管道已经稳定，替换成本最低。

### 方向 2：售后政策构造方案

是否认可「按淘宝/京东/拼多多/抖音/1688 真实规则构造 200~300 条高密度政策文档，切分成 2000 chunk」？

### 方向 3：是否开始拉取可自动化获取的数据

即从 Hugging Face / GitHub 拉取：**Mix-Ecom、CCSE-CS、EcomInstruct、JDivPS、淘宝客服对话**，边拉边整理。

## 7. 风险与注意事项

| 风险 | 应对 |
|---|---|
| 数据集授权 / 许可不明 | 逐份核对 License；商用前确认；合成数据可规避此项 |
| 天池数据需手动下载，阻塞排期 | P0/P1 全自动数据先行，天池数据异步补 |
| 淘宝客服对话可能含手机号 / 地址等 PII | 入库前统一脱敏，与线上 `field_mask` 同一套规则 |
| 合成数据分布与真实偏差，导致评测虚高 | M3 阶段用真实数据重建评测集，合成数据仅用于开发态 |
| 意图 4 分类训练数据不足 | Mix-Ecom 冷启动 + 规则兜底；每类目标 ≥500 条，不足则用 LLM 扩标后人工抽检 |
| 商品库 token 化数据需 pickle 反序列化 | 在隔离环境执行，只读不执行未知代码 |
