## 0. 一句话结论

**能实现。** INTEGRATED_QA_SYSTEM 与文档中「智能客服」的技术底座重合度约 **60–70%**，检索、生成、流式、多轮、评估可直接复用；真正需要新建的是 **多 Agent 编排 + 权限隔离 + 风险控制** 这三层，以及业务域从教育切换到电商客服。

**工作量分布估算**

| 类别 | 占比 | 内容 |
|---|---|---|
| 可直接复用 | 60–70% | 知识工程、FAQ 快速通道、混合召回 + Rerank、HyDE / 子查询、WebSocket 流式、多轮对话、RAGAS 评估 |
| 需改造 | 10–15% | 意图路由 2 分类 → 4 分类、Milvus collection 隔离、评估数据集换域、鉴权前置 |
| 需新建 | 20–25% | Agent 编排层、权限注册表、风控升级 Agent、三套异构系统适配层、新前端 |

> **核心判断**：风险不在「能不能做出来」，而在「业务数据」和「权限/风控规则」两项。前者决定系统是不是真的能用，后者决定它能不能上线。技术侧无卡点。

### 2.3 权限隔离规则 —— 建议你直接确认下表

> **设计约束（重要）**：
> 1. **主 Agent 不持有任何检索器**，只做路由，从架构上杜绝权限泄漏。
> 2. 权限在 **Agent 实例化时静态绑定**（构造注入 retriever / tool 白名单），而非运行时 if-else 判断 —— 静态绑定更可靠、可审计。
> 3. 所有返回给用户的数据统一过一层 `field_mask`（脱敏 + 字段裁剪）。

| 子 Agent | 可读取 | 可调用工具 | **禁止访问** | 脱敏要求 |
|---|---|---|---|---|
| **售前 Agent** | 商品库（名称/规格/价格/参数/库存状态）、活动与优惠券、FAQ | `product.search`、`product.get_price_stock`、`faq.match` | 任何订单数据（含金额、收货信息）、售后政策裁决、其他用户数据 | 无敏感字段 |
| **订单 Agent** | 订单主数据（订单号/商品/金额/状态/物流/平台）、物流轨迹 | `order.get_by_id`、`order.list_by_user`、`order.get_logistics` | 商品成本价/利润、售后政策裁决、营销活动配置、**非本人订单** | 手机号 `138****1234`、姓名 `张**`、地址精确到区县 |
| **售后 Agent** | 售后政策库、工单/退款单、订单中「与售后相关」字段（商品、下单时间、金额——仅用于计算退款） | `policy.match`、`ticket.create`、`refund.calc` | 其他用户订单、商品成本/利润、营销活动配置 | 同订单 Agent |
| **通用 Agent** | FAQ、平台规则、使用指引类知识 | `faq.match`、`kb.search` | **任何用户级数据**（订单、金额、个人信息） | 无 |
| **升级 Agent** | 情绪/金额判定结果、用户身份 | `ticket.create`、`notify.*` | 不参与检索，不生成业务回答 | — |

**需要你确认**：按上表执行 / 你另行提供边界规则。

### 2.4 转人工 / 风险控制规则

#### （1）强情绪判定 —— 建议双层，规则快 + LLM 准

**规则层（毫秒级，先跑）**

- 关键词命中：`投诉` `举报` `曝光` `媒体` `记者` `律师` `315` `消协` `工商` `骗人` `欺诈` `诈骗` `垃圾` `再也不` `退钱` `差评` `找你们领导` `叫你们经理` `报警` `法院`
- 连续 2 轮判定为负向情绪
- 单条消息中感叹号 ≥ 3 个，或全大写/重复字符异常
- 辱骂词表命中

**LLM 层（规则未命中但语义存疑时）**

- 用 DeepSeek 做情绪分级 `0=平和 / 1=不满 / 2=愤怒 / 3=极端`
- **≥ 2 触发升级**

**兜底直通**：用户显式输入 `转人工` / `人工客服` / `我要投诉` → 直接触发，不过模型。

#### （2）大额风险阈值 —— 建议可配置，以下为默认值

| 触发项 | 默认阈值 | 说明 |
|---|---|---|
| 单笔订单金额 | **≥ ¥2,000** | 主阈值 |
| 单笔退款金额 | ≥ ¥1,000 | 售后侧独立阈值 |
| 近 30 天累计退款 | ≥ ¥3,000 | 防恶意/异常 |
| 同一用户 7 天内售后次数 | ≥ 3 次 | 高频风险 |
| VIP / 高价值用户 | 可配（如会员等级 ≥ V3 直接升级） | 体验优先 |

#### （3）转人工落地方式

| 选项 | 说明 | 建议 |
|---|---|---|
| a. 前端提示 + 工单表记录 | 写入 MySQL `tickets` 表，前端展示「已为您转接人工客服」+ 工单号 | **MVP 推荐** |
| b. 对接现有工单系统 API | 直接推送到你们在用的工单系统 | 需你提供接口 |
| c. IM 通知（企微/钉钉/飞书） | 转人工时同时推送群里 | 可作为 a/b 的补充 |

**需要你确认**：情绪判定方式、金额阈值数字、转人工落地方式（a / b / c）。

## 3. 实施架构方案

### 3.1 目录结构（新建部分）

```
agent/
  base.py              # 子 Agent 基类：构造时静态绑定 permission scope
  orchestrator.py      # 主 Agent：意图路由 + 并行风控
  presale_agent.py     # 售前
  aftersale_agent.py   # 售后
  order_agent.py       # 订单
  general_agent.py     # 通用
  escalation_agent.py  # 升级（转人工）
registry/
  permissions.py       # 权限注册表：agent_id -> {retrievers, tools, visible_fields, mask_rules}
adapters/
  product.py  order.py  policy.py   # mock 与 real 同接口，DATA_SOURCE 切换
mockdata/                            # 生成脚本 + 种子数据
milvus/                              # 新 collection: ecommerce_kb（不动现有教育库）
```

### 3.2 单次请求处理流程

```
0  鉴权（user_id / 登录态）
   ↓
1  并行风控：规则情绪检测 + LLM 情绪分级 + 金额阈值检测
   ↓
2  命中 → 升级 Agent（写工单 + 前端提示转人工）→ 结束
   未命中 ↓
3  主 Agent 意图路由：规则优先 → BERT 4 分类 → LLM fallback
   ↓
4  分发到子 Agent（售前 / 售后 / 订单 / 通用），仅能调用白名单内的检索器与工具
   ↓
5  检索 → 生成（子块召回 → Rerank → 父块拼装）
   ↓
6  结果过 field_mask（脱敏 + 字段裁剪）
   ↓
7  WebSocket 流式输出（带 agent_id / card / citations）
   ↓
8  落库（conversations + tickets）
```

### 3.3 关键实现要点

1. **权限静态绑定**：Agent 构造函数注入 `retrievers` / `tools` 白名单，运行时无法越权调用 —— 比 if-else 判断更可靠、可审计。
2. **主 Agent 零检索器**：只做路由决策，不接触任何业务数据。
3. **Milvus collection 隔离**：新建 `ecommerce_kb`，绝不复写现有教育域数据。
4. **统一 field_mask**：所有出口数据强制脱敏 + 字段裁剪，避免各 Agent 各自实现导致遗漏。
5. **风控前置且并行**：与意图路由并行执行，不增加用户感知延迟。

## 5. 风险与注意事项

| 风险 | 应对 |
|---|---|
| 误操作污染现有教育域向量库 | 新建 collection `ecommerce_kb`，旧库只读，禁止 drop/overwrite |

| 环境不通阻塞开发 | 本地 docker-compose 或 Milvus Lite / SQLite 降级方案 |
